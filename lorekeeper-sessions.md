# Lorekeeper — Session Log

The running history, split out of `lorekeeper-master-spec.md` on 9 October 2026. That file had reached 220 KB, a third of it this table, with rows up to 5,700 characters — which is why document previews fell back to raw markdown and it became painful to read.

**Nothing here is current behaviour.** The spec describes how the app works now; this describes how it got there. Read it when you need to know *why* a decision was made, or what a past session already tried.

## About the numbering

Sessions 1 to 36 are kept under the labels they were written with, including the lettered ones (22b to 22d, 35b to 35o). Those letters were a mistake — each was a separate session and deserved its own number — but 169 references across the spec point at these labels, and some plain references like "session 35" mean the whole run rather than that one sitting. Renumbering would have silently changed what those sentences pointed at.

So: the past keeps its labels, and **from session 37 onwards the numbering is plain — no letters, one number per session.**

Two rows cover more than one session each and could not be split, because they were written as a single summary: **35h-k** (four sessions) and **35l-m** (two). Counting those, this log covers about 53 sessions in 49 entries.

## Session 16

**Jun 19**

**Data-loss incident and recovery.** A race condition (autosave firing before initial load resolved) overwrote the real 30MB+ data file with the empty default shape. Recovered characters via independent Companions/Lorebooks/Collections auto-save files; notes and app-only fields (schedule status etc.) were not recoverable. Built three-layer data safety architecture: (1) `dataLoaded` guard blocks autosave until load completes, (2) `main.js` shrink-refuse check rejects any write under 50% of the existing file's size and redirects it to a `.SUSPICIOUS.json` file instead, (3) rolling `lastgood.json` backup on every successful write. Added independent standalone `.md` notes backup per world + global scratchpad (`Notes\` folder), wired from both the right-panel Notes tab and World Info tab, with a "Notes Backups" panel on Batch Import. Also fixed a separate pre-existing bug surfaced during this incident: the inline Site Checklist IIFE inside `DashboardPage` called `useState` after a conditional early-return, violating React's Rules of Hooks and crashing the Dashboard whenever the checklist's item count changed between zero and nonzero — extracted to its own `SiteChecklistPanel` component. Fixed Site Checklist to also flag posted/public items that have never been synced (previously required `site_last_synced_at` to already exist, so never-synced items could never be flagged no matter how many edits). Fixed Schedule tab's status dropdown to auto-stamp `posted_dates` when set to Posted (previously only the Dashboard banner button did this). Discovered and fixed `parseTimestamp()` bug: Saucepan's timestamp format is unparseable by native `Date()`, silently breaking every "local newer" comparison involving a site-imported timestamp. Fixed batch import to preserve the platform image UUID from site exports (was being discarded in favor of local file paths), derive `posted_dates` from the site's `posted_at`/`updated_at` instead of leaving it empty, and use the site's real `updated_at` instead of overwriting it with import time. Added force-import overrides (per-item "Import anyway" button + global "Force import all" toggle) for restoring from a Saucepan companion backup export. Re-fixed four UI width regressions that had silently reverted across project re-uploads (Settings, World Info, Template editor, Persona "New" button) — root cause identified as chat-session fixes not yet being re-synced to project knowledge between turns.

## Session 22b

**Jun 23**

**`selected_chapter_index` correction — not app-only, required by Saucepan on import.** The spec previously stated `selected_chapter_index` is app-only and must be stripped from platform exports. This was wrong: the Baccarat lorebook exported from Saucepan includes `selected_chapter_index: 0`, and Saucepan's import validation requires it. It was removed from all three export paths in session 21/22; this caused Saucepan to reject lorebook imports with "selected_chapter_index: Invalid input: expected number, received undefined". Fixed: `selected_chapter_index: l.selected_chapter_index \|\|0` is now included in `exportLore`, `LoreItemRestoreCard.handleLoreBackup`, and the batch/world ZIP export path. The `validateLore` restore validator correctly does NOT require it (for backward compat with old exports), but the export always includes it. The export strip list in `exportChar` is unaffected — `selected_chapter_index` only exists on lorebooks, not characters.

## Session 22c

**Jun 23**

**`lorebooks` field correction — required by Saucepan on collection import.** Same pattern as `selected_chapter_index` for lorebooks: Saucepan's collection import validator requires a `lorebooks` field (array). Lorekeeper's collection data model uses `companions` for character IDs; `lorebooks` is a separate platform field (lorebooks directly attached to a collection, as opposed to lorebooks from companions). The export was silently omitting it, causing Saucepan to reject collection imports with "lorebooks: Invalid input: expected array, received undefined". Fixed: `lorebooks: c.lorebooks||[]` added to all three collection export paths — `exportColl`, `CollItemRestoreCard.handleCollBackup`, and the world ZIP export path. For collections that don't have a `lorebooks` field stored in Lorekeeper, this defaults to `[]`. **General lesson documented:** Saucepan's import validator requires fields that Lorekeeper's internal model doesn't always store. Both `selected_chapter_index` (lorebooks) and `lorebooks` (collections) must always be included in exports, defaulting to safe empty values. The export strip logic should default-include required platform fields rather than silently omitting them.

## Session 38

**Oct 9**

**Two bugs found by trying to run the backup unattended, and one of them was mine.**

**The app had two app-data folders.** Electron derives `userData` from the app name, and the name depends on how the app was launched: `start.bat` runs `electron .`, which reads `package.json` and gets `lorekeeper`; `start-silent.vbs` runs `electron src/main.js`, which has no `package.json` beside the entry file and falls back to `Electron`. Both launchers ship in this repo, so the same install had two folders — and the GitHub token lives in one of them. A token saved through one launcher was invisible to the other, and to `--backup`. Fixed with `app.setName('Lorekeeper')` in `main.js`, placed before anything reads a path. **It would have bitten silently later**: save a token, switch launchers, backups stop with nothing to explain why.

**The rescue written for that was careless, and destroyed a file.** It looked for a token in the old folders, took the first folder that *contained* one, copied it, and deleted the source. Both old folders existed on the real machine. It took the wrong one, deleted it, and left a file that would not decrypt sitting in the destination — which then made every later attempt exit early and never look at the folder holding the real token. Rewritten to try every candidate, accept one only when it actually **decrypts**, and never delete a source. Tested against the exact state it had created, plus five others.

**And the rescue cannot work on Windows anyway, for a reason worth recording.** `safeStorage` generates a key and protects it with DPAPI, but the generated key lives in a `Local State` file *inside* the userData folder. Move folders and the token travels while the key does not, so the blob stays intact and permanently unreadable. One re-paste fixes it for good. `readToken` now treats an undecryptable file as **absent** rather than as an error, so a bad copy can never mask a good one, and the failure message prints every folder checked and what was in each.

**Confirmed working after that:** `Lorekeeper.exe --backup` runs with no window and reports cleanly, and **a scheduled character posted from the dashboard banner and went public** — the last Stage 0 item that needed a real posting cycle rather than more code. Only the cycle-skip test remains.

**Lessons, both now in the roadmap's working-method list:**

- **A file existing is not a file being valid.** The first rescue checked `existsSync` and called it a token. The fix was to make the validity test *be* the operation that matters — decrypt it — rather than a proxy for it.
- **Never delete the only copy of something to prove a theory about it.** Moving rather than copying turned a recoverable situation into an unrecoverable one, for no benefit at all.
- A corollary that cost real time here: a convenience feature that cannot work on the target platform should say so plainly rather than keep trying. The rescue is kept because it is harmless and correct where the key is shared, but the error message now tells the user to paste the token again instead of implying something is retrievable.

**A retired mechanism left a trap behind, found on the extras script's first real run.** The output said `Created autostash` — the backup clone still held local modifications to Lorekeeper's own data files, left from when this script mirrored them with robocopy. It does not any more, so the clone is now a consumer of those paths and never a producer, which makes every local change to them stale by definition. Left alone, `--autostash` would have stashed and re-applied them on every run, and since the engine rewrites `lorekeeper-data.pretty.json` on nearly every backup, the re-apply would eventually have conflicted — at 11:30pm, unattended, leaving the clone needing hands. The script now discards those paths before pulling. **The general shape is worth remembering: when a mechanism is retired, the state it used to maintain does not retire with it.** It sits there looking like data until something trips over it.

**Both scheduled tasks are live and confirmed**: `Lorekeeper Backup` runs the engine headless with `LastTaskResult: 0`, and `Lorekeeper Extras` runs the script half an hour later so the engine's commit has landed before it pulls.

## Session 39

**Oct 9**

**The rclone engine: Google Drive, OneDrive and Dropbox.** `src/rclone-backup.js`, wired through `github-ipc.js` with a setup panel in Settings. Lorekeeper never handles a cloud credential — rclone owns the OAuth and keeps its token in its own config file, which is the entire reason this route exists instead of a native integration.

**The finding that shaped the design: `rclone sync` deletes everything at the destination that is not in the source.** The docs were ambiguous about it, so it was tested rather than assumed — and a test sync wiped a `README.md` and an unrelated folder. That is the old `robocopy /MIR` footgun exactly, and aimed at someone's Drive it would destroy whatever else was there. So the engine **never syncs a whole destination**: one `sync` per owned folder, each to its own path, and `copy` — never `sync` — for the loose pretty file. All three engines now share one rule: deletion only ever happens inside folders Lorekeeper created.

**File selection was not reimplemented.** A sync stages through the existing `mirrorToFolder()` and lets rclone upload the staging directory, rather than re-expressing the folder list and image exclusion in rclone's filter syntax. The staging copy costs disk, but only changed files are rewritten, and the alternative was the duplicated-logic failure this project keeps recording.

**Config isolation mattered more than expected.** Ine already has rclone installed with her own remotes. Every call passes `--config` at `userData/rclone.conf`, so Lorekeeper neither writes to her config nor depends on what is in it. Staging sits beside it rather than in the data folder — which is what gets backed up, so a second copy of the corpus there would be backed up too.

**Shipping one part untested, deliberately, with a mitigation.** The OAuth sign-in cannot be exercised without a real cloud account, and Ine does not want one as a backup destination. Her call was to ship it flagged. Rather than flag and hope, the first connection now **proves itself**: `verifyRemote()` writes a small file to the destination, reads it back, compares the contents and deletes it, and a connection that fails is **removed rather than kept** — because one that cannot store anything is worse than none, since the panel would report healthy backups. **Two test-environment traps worth remembering, both of which produced a confident wrong result before being caught:**

- **A permissions test is meaningless as root.** `chmod 0o500` on a directory did not stop the write, so the verifier appeared to accept an unwritable destination. The container runs as root, which bypasses file permissions entirely. Re-run against a genuinely impossible path, it refused correctly.
- **An absolute path broke a test, not the code.** The engine strips a leading `/` from the destination path, which is right for a cloud remote (`drive:Lorekeeper`) and wrong for the absolute local path the test harness passed. The files went somewhere relative to the working directory and the assertions read `false`. The fix was to root the test remote with rclone's `alias` backend, not to change the engine.

Both are the same lesson from a different angle: **when a test fails, establish whether the code or the test is wrong before changing either.** Both of these would have produced a worse engine if the first instinct had been trusted.

**Still unverified and recorded as such:** the OAuth flow itself, and whether the bundled binary resolves in a packaged build. `package.json` carries the `extraResources` mapping; `vendor/rclone/rclone.exe` has to be placed by hand before a build.

**The colour picker took five rounds, and four of the five were my fault in instructive ways:**

1. **Averaging a 5x5 or 11x11 patch in sRGB gives brown.** sRGB values are gamma-encoded, so the arithmetic mean of encoded numbers is not the mean of the light. Averaging a saturated red next to a saturated cyan in encoded space lands on mud. Decode to linear light, average, re-encode — and the patch readings became what the eye expects.
2. **A silent `return` where the bitmap was missing** meant the second click did nothing at all, with no error anywhere. Any early exit on a user action needs to be distinguishable from a successful one.
3. **The canvas display size and its bitmap size had drifted apart**, so the click coordinates addressed the wrong pixel. Rebuilt around an `<img>` with an offscreen canvas, which removes the chance of the two disagreeing.
4. **CSS `zoom` on `<html>` breaks pointer maths in Chromium — and this project had already solved that once, in `CropTool`.** At zoom 1.25 the computed row ran past the end of a 468-row bitmap at about 81% down the image, so every click below that clamped to the last row and returned the same colour. Ine's report — *"if i click somewhere below that line, it doesn't pick the color"* — described the symptom precisely. The failure here was not the bug, it was writing the second copy of pointer maths instead of reusing the working one. They are consolidated now.
5. **An `onLoad` race** behind a `ready` flag that could be set after the first paint. Removed the flag rather than sequencing around it.

Both were wrong, and Ine corrected them: the canonical forms are `{{sub}}`, `{{obj}}`, `{{poss}}`, `{{poss_p}}` and `{{ref}}`, and every pronoun word — `{{they}}`, `{{them}}`, `{{their}}`, `{{him}}`, `{{his}}` — is a working alias for one of them. She uses the `they` variants because they are memorable, not because they are the real names.

**So `MACROS` is a reference list, not an allowlist, and nothing may validate against it.** A linter that flagged `{{him}}` as unknown would be flagging correct input. This is now recorded in the spec, because it is exactly the kind of thing a future session would "fix".

The other rule worth having written down: in `{{s?a:b}}` and `{{p?a:b}}`, **the first value is the one that gets used**. `{{s?was:were}}` is the singular form; the plural is `{{p?were:was}}`. **The real find: a fresh install was running the retired batch script.** Running the packaged build with backup set to **None** launched `lorekeeper-sync.bat` and wrote a 33 MB pretty data file — precisely the behaviour the packaging checklist exists to prevent.

The chain: `activeProvider()` read the module-level `syncPaths` cache before falling back to the data file. `resolveSyncPaths()` runs a one-time migration that adopts the legacy constants — including `provider: 'github'` — whenever `I:\LorekeeperBackup\lorekeeper-sync.bat` happens to exist on the machine. **And the fix appeared to fail, because there were three writers and I had found one.** A rebuilt packaged build, launched with backup on None, wrote the file again. The asar was newer than the patched `main.js`, so the gate was in the build and had let it through — which narrowed it immediately.

**The file names its own author.** `sync-paths.cmd` contains a `SRC=` line holding whatever `DATA_DIR` the writing process had. It read `I:\Lorekeeper\dist3\win-unpacked`, which proved a packaged build wrote it and ruled out the development instance in a single command. **When something writes a file it should not, read the file before reading the code** — the earlier guess that a surviving dev instance was responsible was wrong, and the file said so in one line.

The other two writers:

- **`set-sync-paths` wrote the file unconditionally**, on every Settings change, whatever the route, and read an absent provider as `'github'`. Now defaults to `'none'` and writes only for a script route.
- **The renderer seeded `backup_repo_dir` from the legacy migration.** `getSyncInfo().backupDir` resolves through `resolveSyncPaths()`, so a fresh install adopted `I:\LorekeeperBackup` into its own settings with the provider still correctly reading `none` — which is exactly what the fresh data file showed. The comment four lines above that seed already argues that seeding the *provider* would hand a fresh install a destination it never chose. **The argument was written down, correctly, and then not applied to the field directly beneath it.**

That also explained a timing oddity that had looked like contamination: the first launch of the fresh build wrote nothing, because no data file existed yet; the second wrote the file, because by then Settings had been visited and the seeded path pushed through. **An intermittent symptom was state being created by the first run and read by the second**, not a flaky test.

With all three fixed, a fresh packaged build shows None with an empty repo folder and writes nothing anywhere. **Stage 3b's packaging pass is closed.**

**I introduced a second bug while fixing the first, and caught it before it ran.** The startup gate was written as `prov0 === 'github' || prov0 === 'folder'`. `folder` is the *new* in-app folder-copy route, which never touches the batch script; the script route is `github` or `legacy-folder`, which is what the shutdown gate four hundred lines away already used. Left alone, a fresh install set to plain-folder backup would still have written a generated file into a backup folder it does not use. The lesson is the one this project keeps recording from new angles: **when the same decision is expressed in two places, read the other one before writing yours.**

**The silent-stale-write mystery is solved, and it was my tooling, not Ine's machine.** Twice this session a file was reported written and the old bytes stayed on disk, and twice I doubted Ine's account of her own machine before she stated plainly that she closes and restarts Lorekeeper after every change. The cause: committing from a staged container path reports success and writes nothing, while committing the identical bytes as a sent file lands. **Reading the byte count back off the disk is now the only acceptable proof that a write happened**, and a tool's own success report counts for nothing.
